# FetchX Native Messaging Host

This is the Rust binary that bridges the browser extension to the FetchX
desktop application. The browser launches it as a child process through its
native messaging API (Chrome/Edge or Firefox).

## How it works

```
Browser extension
      ↓  stdin/stdout (4-byte LE length + JSON)
Native messaging host  (this binary)
      ├─ local target → loopback TCP + session token → FetchX desktop application
      └─ remote target → HTTPS + bearer token → FetchX remote server
```

The host reads exactly **one** native-messaging request from stdin, forwards it to
the selected target, writes the response to stdout, and exits. The browser opens
a new host process for each request. Local download operations continue through
the desktop's existing CoreServices and queue.

## Security model

- The host binds to `127.0.0.1` only.  No LAN or internet exposure.
- A per-session UUID token (generated by the desktop at startup) is required on
  every connection.  The token is written to a user-private file; other OS users
  cannot read it.
- Message size is bounded at 64 KiB.  Larger frames are rejected before allocation.
- No shell execution.  Structured arguments only.
- The host never handles cookies or browser credentials.
- Remote targets must use HTTPS; HTTP is accepted only for loopback testing.
  Redirects and environment proxies are disabled, requests have timeouts, and
  response bodies are size-bounded.
- Remote bearer tokens are stored in Windows Credential Manager, keyed to both
  the target ID and a fingerprint of its endpoint. Tokens are not stored in
  browser extension storage. The host verifies `fetchx.rpc.v1` discovery and
  currently allows only `system.discover`, `download.create`, and
  `download.list` for browser RPC forwarding.
- Credential-backed remote targets are supported by the Windows host. Other
  platforms can continue to use the local desktop target.

## Building

```sh
cargo build --release -p fetchx-native-host
```

The resulting binary is at `target/release/fetchx-native-host` (or `.exe` on
Windows).

## Installation (Windows)

1. Build the release binary (above).
2. Load the extension from FetchX Settings → Browser extensions. The extension
   uses a fixed Chromium ID, so no ID argument is needed.
3. Run the installation script to register the native messaging host:

```powershell
cd apps\browser\native-host\manifest
.\install-windows.ps1
```

This writes the native messaging host manifest to `%APPDATA%\fetchx\native-host\`
and registers the native host in the Windows Registry. It does not install the
browser extension; use **Load unpacked** in the browser's extension page.

To uninstall:

```powershell
.\install-windows.ps1 -ExtensionId "your32characterextensionidhere" -Uninstall
```

### Firefox

Firefox uses a separate host manifest and registry entry. Its manifest allows
the fixed extension ID `FetchX@FetchX.app` in `allowed_extensions`, so it does
not overwrite the Chrome/Edge `allowed_origins` manifest.

After building the release binary, run:

```powershell
cd apps\browser\native-host\manifest
.\install-firefox-windows.ps1
```

The script registers the native host only. Use **Load Temporary Add-on** in
Firefox and select the `manifest.json` from FetchX Settings → Browser extensions.
Temporary add-ons are removed when Firefox exits; a permanent Firefox add-on
must be signed. To uninstall the Firefox native-host registration:

```powershell
.\install-firefox-windows.ps1 -Uninstall
```

## State file location

The desktop application writes a JSON state file on startup so the native host
can find its loopback port and session token:

| Platform | Path |
|----------|------|
| Windows  | `%LOCALAPPDATA%\com.fetchx.desktop\browser-ipc.json` |
| Linux    | `$XDG_RUNTIME_DIR/fetchx/browser-ipc.json` |
| macOS    | `~/Library/Application Support/com.fetchx.desktop/browser-ipc.json` |

The state file is removed when FetchX shuts down.

## Extension ID

The native messaging host manifest must allow the exact extension ID. Chrome
and Edge use `allowed_origins`; Firefox uses `allowed_extensions`. The
development Chromium ID changes depending on the machine and whether the
extension is packed; Firefox uses the fixed ID `FetchX@FetchX.app`.

**Development flow:**

1. Load the `apps/browser/extension/` directory as an unpacked extension in
   `chrome://extensions/`.
2. Note the generated extension ID (a 32-character lowercase string).
3. Run `install-windows.ps1` with that ID.
4. Reload the extension if you update it.

For production deployment, a packed extension has a stable ID derived from its
signing key.  See [Chrome's documentation](https://developer.chrome.com/docs/extensions/reference/manifest/key)
for details on generating a stable ID.
